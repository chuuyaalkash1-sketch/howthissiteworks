короче я сначала делала это как обычный реакт сайт, поэтому когда я нажимала между проектами браузер не перезагружал всю страницу. реакт уже был загружен и просто менял нужный кусок внутри страницы. из-за этого могло казаться что меняется только header или пара div, а в network почти ничего нового не появляется

сейчас я это сделала понятнее. у корневого блока приложения меняется class и data-page в зависимости от текущего раздела. например на главной это `page-home`, в магазине `page-shop`, в knowledge base `page-knowledge`, в симуляциях `page-simulations`. то есть если я смотрю вкладку elements, я прямо вижу что состояние страницы реально поменялось, а не только текст в header

при этом я не делала четыре разных фронтенда. у меня остается один общий реакт интерфейс, потому что по задаче это один проект. просто внутри него есть разные разделы и у каждого свой мейн и свои компоненты

например я нажимаю shop

1. обработчик react вызывает `navigate("/shop")`
2. через `history.pushState` меняется url без полной перезагрузки страницы
3. react меняет `path`
4. из-за нового `path` вместо предыдущего компонента рендерится shop
5. у `app-shell` меняется class на `page-shop`, а `data-route` становится `/shop`
6. отдельный telemetry запрос уходит на `/api/observability/events` с событием `route_changed`
7. этот запрос видно в network
8. gateway отправляет его в observability service
9. observability пишет json событие в stdout контейнера
10. filebeat читает stdout docker контейнера, logstash принимает событие, приводит его к общей схеме и отправляет в elasticsearch
11. kibana уже читает эти документы из elasticsearch

то есть изменение dom и network запрос это две разные вещи. сам реакт может поменять div вообще без запроса в сеть. поэтому я отдельно добавила telemetry, чтобы пользовательские переходы тоже были видны в elk

при переходе между разделами у меня появляется `post /api/observability/events` с событием `route_changed`

я не хочу чтобы фронтенд знал адрес каждого контейнера отдельно. браузер обращается к одному адресу `/api/...`, а gateway уже решает куда запрос отправить

примерно так:

```text
browser
  -> gateway
       -> auth
       -> content
       -> commerce
       -> files
       -> observability
```

регистрация идет в auth, оценки в content, заказ в commerce, файлы в files, события интерфейса в observability

у меня observability не должен тормозить обычную работу сайта. сервисы делают свою задачу и пишут структурированное событие. дальше логовый pipeline живет отдельно

```text
service stdout
  -> filebeat
  -> logstash
  -> elasticsearch
  -> kibana
```

filebeat это агент который забирает логи контейнеров. logstash их разбирает и нормализует. elasticsearch хранит и индексирует документы. kibana нужна уже чтобы искать, фильтровать и визуально смотреть что происходило

я разделила старый бекенд потому что раньше один питон процесс делал вообще все. теперь auth отвечает только за аккаунты и jwt, content за рейтинг и контент, commerce за заказ, files за пользовательские файлы, observability за события, а gateway является одной точкой входа для фронтенда
