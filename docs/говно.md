# как у меня все работает

короче я сначала делала это как обычный react сайт, поэтому когда я нажимала между knowledge base, shop и simulations браузер не перезагружал всю страницу. react уже был загружен и просто менял нужный кусок dom внутри страницы. из-за этого в devtools могло казаться что меняется только header или пара div, а в network почти ничего нового не появляется.

сейчас я это сделала понятнее. у корневого блока приложения меняется class и data-page в зависимости от текущего раздела. например на главной это `page-home`, в магазине `page-shop`, в knowledge base `page-knowledge`, в симуляциях `page-simulations`. то есть если я смотрю вкладку elements, я прямо вижу что состояние страницы реально поменялось, а не только текст в header.

при этом я специально не делала четыре разных фронтенда. у меня остается один общий react интерфейс, потому что по задаче это один educational project. просто внутри него есть разные разделы и у каждого свой `main` и свои компоненты.

## что происходит когда я нажимаю на вкладку

например я нажимаю shop.

1. обработчик react вызывает `navigate("/shop")`.
2. через `history.pushState` меняется url без полной перезагрузки страницы.
3. react меняет state `path`.
4. из-за нового `path` вместо предыдущего компонента рендерится shop.
5. у `app-shell` меняется class на `page-shop`, а `data-route` становится `/shop`.
6. отдельный telemetry запрос уходит на `/api/observability/events` с событием `route_changed`.
7. этот запрос видно в network.
8. gateway отправляет его в observability service.
9. observability пишет json событие в stdout контейнера.
10. filebeat читает stdout docker контейнера, logstash принимает событие, приводит его к общей схеме и отправляет в elasticsearch.
11. kibana уже читает эти документы из elasticsearch.

то есть изменение dom и network запрос это две разные вещи. сам react может поменять div вообще без запроса в сеть. поэтому я отдельно добавила telemetry, чтобы пользовательские переходы тоже были видны в elk.

## что теперь видно в network

при переходе между разделами у меня появляется `post /api/observability/events` с событием `route_changed`.

еще я добавила события `ui_click` для кнопок и ссылок и `form_submit` для отправки форм. я специально не отправляю туда значения паролей, токены и содержимое файлов. в лог идет только тип действия, текущая страница и безопасное название элемента.

например можно увидеть примерно такое:

```json
{
  "service": "frontend",
  "event": "route_changed",
  "page": "shop",
  "path": "/shop"
}
```

или:

```json
{
  "service": "frontend",
  "event": "ui_click",
  "page": "knowledge",
  "control": "отправить оценку"
}
```

а сама отправка оценки уже делает отдельный настоящий api запрос `post /api/ratings`. регистрация делает `post /api/auth/register`, загрузка файла делает `post /api/uploads`, заказ идет в commerce service. это уже не просто telemetry, это реальные бизнес запросы.

## зачем тут gateway

я не хочу чтобы frontend знал адрес каждого контейнера отдельно. браузер обращается к одному адресу `/api/...`, а gateway уже решает куда запрос отправить.

примерно так:

```text
browser
  -> gateway
       -> auth
       -> content
       -> commerce
       -> files
       -> observability
```

регистрация идет в auth, оценки в content, заказ в commerce, файлы в files, события интерфейса в observability.

## как elk получает события

у меня observability не должен тормозить обычную работу сайта. сервисы делают свою задачу и пишут структурированное событие. дальше логовый pipeline живет отдельно.

```text
service stdout
  -> filebeat
  -> logstash
  -> elasticsearch
  -> kibana
```

filebeat это агент который забирает логи контейнеров. logstash их разбирает и нормализует. elasticsearch хранит и индексирует документы. kibana нужна уже чтобы искать, фильтровать и визуально смотреть что происходило.

важный момент: kibana сама логи не собирает. она показывает то что уже лежит в elasticsearch.

## почему раньше elk как будто ничего не видел

раньше переход внутри react мог быть чисто локальным. я нажала вкладку, react поменял компонент, но backend вообще не участвовал. значит filebeat и elasticsearch тоже не могли узнать что я куда-то перешла.

теперь для таких действий есть browser telemetry. поэтому даже spa переход оставляет отдельное событие и его можно увидеть сначала в network, потом в observability и потом в elasticsearch/kibana.

## нужно ли было делать отдельный процесс для каждой вкладки

нет. отдельный процесс только ради того чтобы в network что-то мигало не нужен. это было бы искусственно.

отдельные процессы у меня как раз там где это имеет смысл на backend: auth, content, commerce, files, observability и gateway запускаются как отдельные сервисы/контейнеры. frontend в браузере остается одним react приложением.

если потом захочу чтобы при первом открытии каждого большого раздела браузер еще скачивал отдельный js файл, можно сделать react lazy + code splitting. тогда vite соберет shop, knowledge и simulations в отдельные chunks и в network при первом открытии раздела будет видна загрузка этого chunk. но это оптимизация загрузки, а не обязательное условие для elk.

## как я объясняю микросервисы

я разделила старый backend потому что раньше один python процесс делал вообще все. теперь auth отвечает только за аккаунты и jwt, content за рейтинг и контент, commerce за заказ, files за пользовательские файлы, observability за события, а gateway является одной точкой входа для frontend.

это удобно еще и для kubernetes, потому что каждый сервис потом можно масштабировать отдельно. например gateway можно держать в трех pod, а auth в двух. при rolling update kubernetes поднимает новый pod, проверяет readiness и только потом убирает старый, поэтому сервис не должен полностью исчезать во время обновления.

## что я могу показать в devtools

чтобы быстро показать что все реально работает я делаю так:

```text
f12 -> network -> фильтр observability
```

потом перехожу `catalog -> knowledge -> shop -> simulations` и показываю новые `post /api/observability/events`.

потом убираю фильтр и показываю реальные api запросы: регистрацию, рейтинг, загрузку файла или заказ.

во вкладке elements можно выбрать корневой `.app-shell` и увидеть как у него меняется `page-home`, `page-knowledge`, `page-shop`, `page-simulations` и `data-route`.

после этого можно открыть kibana и найти эти же события уже после прохождения filebeat -> logstash -> elasticsearch.

## что я не логирую

я специально не должна складывать в elk пароль, jwt token, содержимое пользовательского файла и другие секретные данные. иначе observability сама превращается в дыру по безопасности.

я логирую действие и технический контекст, а не секретное содержимое.
